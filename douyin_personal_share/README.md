# Douyin personal recommendation sharing

Standalone Python tool for reading the logged-in account's recommendation feed and optionally sharing canonical video links to one configured Douyin user.

## Setup

```powershell
cd D:\deepseek\repo\douyin_personal_share
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item config.example.json config.json
```

The tool uses installed Microsoft Edge (`channel="msedge"`) and does not need a downloaded browser. `tzdata` supplies the Singapore timezone database on Windows. Browser temporary files go into ignored `playwright-temp/`; set `DOUYIN_PLAYWRIGHT_TEMP` to use a different directory. If Edge is unavailable, install Chromium and change the launch channel in `douyin_share.py` to `"chromium"` after running `playwright install chromium`.

Fill `recipient_profile_url` with the user's profile URL and `recipient_handle` with the exact visible Douyin ID. A Douyin ID can differ from the opaque token in the profile URL; the tool never treats them as interchangeable. No credentials or recipient details belong in tracked files. The example values are blank.

Run `python douyin_share.py --login`, complete login manually in the visible browser, then press Enter in the terminal. The persistent browser profile is stored in `browser-profile/`. Run `python douyin_share.py --verify-recipient` to check the configured Douyin ID on the profile, open the matching chat without sending, and create a local verification marker. Then run `python douyin_share.py` to inspect candidate recommendations in dry-run mode.

Run `python douyin_share.py --browse` to open a visible, read-only session on the normal `推荐` tab (10 minutes by default; `--minutes` accepts 1–15). The tool first opens the site's `精选` landing page, then selects `推荐`; it stops if that tab is missing and never falls back to `精选`. For videos that actually play for at least 8 seconds, it captures up to 12 seconds of the video element's audio in memory for local offline transcription, and up to three visible video frames for the configured vision service. It stores the title, transcript, brief content summary, tags and playback duration in up to 30 recent records at `../bridge/state/douyin-interest-memory.json`. The QQ and Douyin owner-reply prompts both read the latest five records as interest context after the bridge process is restarted. Audio/frame capture may be unavailable for some videos, in which case the title and watch record can still be saved. This command does not like, follow, comment, or send messages. It is manual and does not change the existing scheduled task. When the owner invokes the same bounded read-only flow in QQ private chat with “自己刷一会儿抖音”, the bridge queues the request to the persistent inbox listener so it uses the already-open, authenticated Edge session instead of attempting to launch a second browser for the same profile. The listener returns to the verified inbox after browsing. The assistant reviews returned video summaries and suggests skip/like/comment-draft decisions (up to two like suggestions and one comment draft). This is an initial dry-run: suggestions are shown to the owner but no automatic likes or comments are made. A comment draft is never presented as a published comment or a verified @ mention. The QQ flow remains limited to 1–5 minutes.

The owner can also invoke `douyin_interact_with_video` in QQ private chat for one explicitly identified canonical video URL. `action=like` is idempotent and only clicks when the page exposes a uniquely identifiable, confirmed unliked control. `action=comment` requires the exact one-line text supplied by the owner; the tool never invents public text. Use `dryRun=true` to inspect the like/comment controls without publishing an interaction. Actual actions require an explicit request; uncertain results are saved in ignored `interaction-state.json` and are not retried automatically. All operations queue for the browser profile lock for up to five minutes.

`python douyin_share.py --inspect-inbox` opens the verified chat and prints sanitized DOM structure only (classes, attribute names, and counts; no message text). Inbound replies remain disabled unless `inbound.enabled` and `inbound.selectors_verified` are true and all selectors are configured after DOM review. `--poll-inbox` handles at most one newest unseen message; its first run only records a baseline and sends nothing. Douyin currently exposes no stable message ID in the rendered web UI, so the poller uses a local fingerprint of the incoming row's order and text; a major UI reorder can require resetting `inbound-state.json` and baselining again. The persistent `--listen-inbox` mode keeps the verified conversation open and uses a page-side `MutationObserver` to notice message-row changes. It still requires `reply_backend.enabled`, the configured bridge owner QQ/handle mapping, and the local console-token file. The listener retries after browser/session failures and resumes after each scheduled send or daily browse.

Sending requires the verification marker to match the configured profile URL and handle. Scheduled sends also obey `daily_max` (default 5, maximum 5). Before every send, the tool opens the configured profile, confirms its visible Douyin ID, opens the message inbox, and selects the unique conversation whose display name matches that verified profile. It then checks the visible conversation editor and the unique send control. If a check fails, it stops. Each attempted video is saved before clicking Send, so an ambiguous result cannot be retried automatically; inspect the conversation and local `state.json` before clearing an attempt. Each message contains the video's canonical public page URL, its title, and the author when available. Attempted video URLs are deduplicated in `state.json`.

`run_listener.ps1` starts `--listen-inbox` at user logon through the `DaFeiYu-DouyinInboxListener` task. While active, the listener checks saved send slots every 15 seconds, opens Edge for scheduled sends or the daily browse only when due, then returns to the verified inbox. It requires the Windows user to remain logged in and keeps Edge open on the Douyin conversation. The listener task restarts after failures and has no one-hour execution limit. The existing `DaFeiYu-DouyinShare` task remains as a 15-minute fallback; `run_daily.ps1` skips its browser work while the listener owns the browser profile. Manage both in Windows Task Scheduler under Task Scheduler Library.

Set `scheduled_enabled` in `config.json` to `false` to pause automatic sends. The listener continues watching the inbox, but skips scheduled video shares. Set it back to `true` to resume. This switch only controls scheduled runs; manual commands such as `--send` are unchanged. Existing configurations default to `true` to preserve their current behavior.

The tool persists five randomly chosen Singapore local times per day, one in each window: 09:00–11:30, 11:30–14:00, 14:00–17:00, 17:00–20:00, and 20:00–23:00. Each poll launches Edge only when a pending time is due. It accepts a run up to 25 minutes late; older missed slots are marked skipped. At most one item is attempted per slot. A slot is recorded as attempted before Edge opens, so failures and ambiguous sends consume that slot and are not retried. The persisted plan is in `state.json`.

The share collector explicitly selects the normal `推荐` tab, then selects the first eligible cards in feed order, requires a title and canonical `/video/<id>` URL, avoids duplicate URLs, and prefers distinct authors. The separate `--browse` mode records observed playback as a lightweight interest signal; it does not automatically like or comment. Messages use the canonical public `/video/<id>` page. A native video-card send action is still unverified. Before enabling scheduled sends, verify the logged-in account and recipient inbox with the manual setup commands; Douyin can still change its page markup. An unrecognized layout fails closed. Use only with an account and recipient you control and in accordance with Douyin's terms.

Douyin's official mini-program documentation lists the proactive message API scope as `im.direct_message` and says the mini-program operator must apply for the capability in the developer console: [Private and group messaging overview](https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/develop/tutorial/open-capabilities/management/private-domain/private-and-group-message). This module uses the visible website UI and does not call that API.

## State and safety

`state.json` contains attempted and confirmed video URLs plus per-day counts. `inbound-state.json` tracks consumed inbound message IDs only. `bridge/state/douyin-interest-memory.json` contains recent watched video titles, authors, public URLs, observed playback duration, short transcript excerpts, summaries and tags; it is local runtime state and is not tracked by Git. Audio transcription uses the existing local offline speech model. Video frames are sent to the configured vision endpoint (`stickerVisionBaseUrl`), which may use a remote model according to that service's configuration. The browser profile contains account session data; keep all local state out of source control. All browser modes use an exclusive lock and fail closed if another run owns the profile or a stale lock remains. Dry-run is the default. No real messages are sent by the included tests.

The optional inbound-reply bridge is disabled by default in `config.json`. Enabling `reply_backend` lets the module request a reply from the local QQ bridge; the bridge must separately have `douyinOwnerQQ` set to the owner's QQ number and `douyinOwnerHandle` set to the exact configured Douyin ID. The bridge uses a separate DSH session for Douyin and injects shared owner memory as historical context. The module reads the existing local console token file at request time; it is not copied into config. Inbound IDs are consumed before model work, so timeouts and ambiguous outcomes are not automatically retried.

The current web UI's incoming/outgoing classes and text-message node have been inspected. The backend gate and selector-driven poller are present, but the example configuration keeps them disabled. Shares continue to use a canonical video URL and short note because a native video-card send action has not been verified in the current web UI.
