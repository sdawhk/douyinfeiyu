# 唱歌技能包机制与项目现状

核对日期：2026-10-30。此文档是开发用项目记忆，不是机器人的群友长期记忆（`dsh-memory`）。代码与运行配置变化后，应重新核对状态。

## 技能包怎样“唱歌”

本机源包：`C:\Users\admin\Desktop\流萤音色语音加唱歌技能包4.0\dafish-sing-skill-20261023`。核心文件为 `payload/src/mcp-sing.js`、`payload/sing/cover.py` 和 `models/sing/`。它在 DSH 中注册 `mcp-sing` stdio 服务，暴露三个工具：

1. `sing_probe` 检查 yt-dlp、ffmpeg、Python、torch、demucs、RVC 推理代码和模型。
2. `sing_search` 先试 B 站公开搜索接口，再用 yt-dlp 的 B 站搜索，最后退到 YouTube 搜索，返回候选歌曲。
3. `sing_cover` 重新搜歌并选候选，yt-dlp 下载音频、ffmpeg 截片段。`mode=original` 直接输出原唱片段；`mode=ai` 先用 demucs 分出人声和伴奏，再由 `cover.py` 调 RVC `VoiceConverter` 把人声换成 `liuying.pth` 音色，最后用 ffmpeg 混回伴奏。产物保存为 `audio/sing-*.mp3`，工具返回文件名，随后还需调用 QQ 发语音工具。

RVC 用 `contentvec` 提取内容特征、`rmvpe` 提取音高；`liuying.pth` 决定目标音色。它是对现有音源的变声翻唱，不负责从文字生成新的曲调或演唱。`mode=original` 也不是流萤演唱。

按当前 `mcp-sing.js`，片段默认 30 秒，允许 5–240 秒。包内 README、角色卡和文件头还有“最长 60 秒”的旧描述，应以工具参数 `MAX_SECONDS = 240` 为准。`-VoiceTool` 的安装说明称可改发送工具名，但当前 `mcp-sing.js` 的 `next` 字段仍写死 `qq_send_voice`，接到别的后端时须实测实际工具名，不能只依赖安装说明。

## 本项目现有唱歌链路

`bridge/src/song-cover.mjs` 按技能包思路接入现成歌曲：B 站搜索接口优先，失败后依次试 yt-dlp 的 B 站和 YouTube 搜索；yt-dlp 下载音频，ffmpeg 默认从约 30 秒处截取 60 秒的片段；整首歌按不超过 60 秒分段。搜索过滤伴奏、KTV、短剧、歌单等误匹配，并优先排完整歌名；单字中文歌名也可以点唱，例如“唱嘲”，检索按标题边界匹配，避免把“嘲笑”当成《嘲》。不完全匹配时 `bridge/src/qq-bot.mjs` 先列候选，等点歌人明确指定歌名或 `#序号`，避免把别的音频冒充所点的歌。`唱歌 歌名` / `翻唱 歌名` 以及 `唱一首雨夜 DJ 版的歌` 等自然说法使用 `bridge/src/rvc-singing.mjs` 把人声转成流萤音色；群聊开头 `@机器人` 也能识别。群聊点歌先确认对象：明确 @ / 引用机器人、以 `唱歌/翻唱/原唱/搜歌 歌名` 等命令开头、使用已开启的歌单命令，或在同一会话接续机器人刚发出的歌曲才进入点歌路由；无法确认对象的自然语言按静默处理，不触发主人/白名单权限提示。`原唱 歌名` 直接发送原唱片段，`搜歌 歌名` 只列候选。自然说法可指定 5–240 秒片段，如 `唱10秒钟雨夜`；暂不支持在聊天里指定起始秒数。`bridge/src/qq-bot.mjs` 对歌单外的新歌默认只放行主人，运行设置的 `singing.allowedQQs` 可放行指定 QQ；本地歌单成品可供群友点播，歌单内整首可按要求分段发送，Mureka 原创仍只允许主人。最后以 OneBot `record` 段把音频发到 QQ。B 站返回 412 时会尝试 YouTube；Windows 上 yt-dlp 的 Python 进程若临时 `EPERM`，会短暂重试。

`bridge/src/singing.mjs` 保留 Mureka 的 `song/easy-generate` 原创短歌链路，命令为 `原创唱歌 主题`。现成歌曲点唱不要求 Mureka Key，运行设置中的开关是 `singing.coverEnabled`；原创歌曲仍需另行启用及填写 Key。现成歌曲翻唱与原创歌曲 RVC 转换共用音高设置。

候选清单按群/私聊、发言人和检索词在内存中保留 10 分钟；主人随后用 `#序号` 选歌时复用同一清单，防止搜索结果变动后选中另一首。重启后缓存自然失效，需要重新搜歌。

制作完成的歌曲语音持久保存到 `bridge/state/song-cache/`，文件以歌名、模式、候选、片段起止和音色参数生成的 SHA-256 标识；相同请求会直接复用本地 MP3，避免再次搜歌、下载或 RVC 转换。现成歌曲缓存还会按标点和空格别名回查，例如“雨爱司凤版”可复用“雨爱（司凤版）”的成品，但仍核验模式、片段、音色和音频哈希。QQ 上传前即保存新成品，发送失败后重试点歌不必重新制作。Mureka 原创歌按主题及转换音色设置缓存。最近一首同时按点歌人 QQ 号保留到 `bridge/state/recent-song-<QQ>.bin/.json` 一小时，用于“唱出来”或跨群重发。“再来一段”“再来一段60秒的”先查本地对应片段缓存；没有成品才从上一段终点继续制作并保存。

自然点歌仍是“搜索现成歌曲并翻唱”，不会把模型临时写出的歌词谱曲成新歌。QQ 群里真实的 `@机器人 唱一首雨夜dj版` 可能在提取文本后保留 `@昵称` 前缀；点歌解析需使用 OneBot 登录昵称或真实 @ 信息先识别该前缀，并在消息合并前走直达处理。只回复“霓虹风”之类的风格词不会自行触发点歌。

`bridge/src/rvc-singing.mjs` 和 `bridge/scripts/setup-singing-rvc.ps1` 把技能包的 `cover.py`、RVC 代码与模型放到 `D:\deepseek\state\singing-rvc`。启用 RVC 时，音频经 ffmpeg 规范化、demucs 分离人声、`cover.py` 做 RVC 转换、ffmpeg 混音，然后发 QQ 语音；普通 TTS 也有单独的 RVC 开关。`bridge/scripts/setup-song-cover.ps1` 负责补齐 yt-dlp 与 Demucs 的 `sphn` 依赖，运行产物留在 `state/`。该工作区还有其他未提交改动，修改时保留它们。

翻唱前用 Demucs 人声轨与伴奏轨的音量判断片段是否有可用人声；人声过弱时不发送只有伴奏或严重伪声的结果。下载所选音源失败时会自动尝试其他同歌名匹配候选；全部失败后群聊只发送简短失败提示，具体错误仅记入本地日志。RVC 后混音降低伴奏，并在 300 Hz 附近轻削浑浊、在 3.2 kHz 附近轻推人声清晰度，最后限幅。当前人声增益为 1.0、3.2 kHz 增益为 +1 dB，混音配置使用独立的 `clear-v4` 缓存版本，避免继续复用旧混音。翻唱成品输出为 48 kHz、双声道、192 kbps MP3，输入规范化仍为 44.1 kHz。这个检查只验证有可听人声，无法证明歌词与点歌者心中的版本一致；具体版本依赖搜索标题和用户指定候选。

这台机器上已看到 `cover.py`、`liuying.pth`、`rmvpe.pt`、`contentvec`、ffmpeg、虚拟环境 Python及点唱依赖。已实测搜歌、下载、截取 5 秒音频并完成流萤 RVC 转换；未向 QQ 发送测试消息。

## 接入或排查时的边界

- 2026-10-30 当前 `PREVIEW_ENABLED=false`、`RED_PACKET_ENABLED=false`：30 秒试听、新歌试听和红包记账入口停用；本地歌单仍展示已校验的 60 秒左右流萤翻唱成品，所有群友可用“点歌1”播放单段；发歌单后的 5 分钟内也可直接回复有效序号点歌一次，随后说“发整首”或“唱完整首 歌名”可免费分段唱歌单内的整首；“唱《歌名》的完整版”“把《歌名》唱完整”等说法会识别为同一请求。歌单外的新歌与整首仍需主人权限，普通新歌可由后台 QQ 白名单授权；Mureka 原创及管理员权限不随白名单开放。歌单编号由主 QQ 桥接处理，侧车不抢请求；保存运行设置后约 5 秒热更新。

- 扩展候选选择、片段长度或发送范围时，保留现成歌曲与 Mureka 原创歌各自的触发入口和设置。
- 生成音频和发送 QQ 是两个独立步骤，分别记录成功或失败。RVC 未就绪时要报缺项，不把原唱伪装成流萤翻唱。
- 运行模型、Python 环境和音频暂存留在 `state/`，不要复制进仓库或 `dsh-memory` 数据库；后者保存聊天记忆，不承担技能安装或工程知识管理。
- 更新能力说明时同时核对 `bridge/README.zh.md`、运行设置文案和本文件，避免把原创唱歌与现成歌曲翻唱混淆。
